# ISUCON のチューニング手法

ISUCON で効く手法の一覧。Analyst が仮説を作るとき、人間が示唆を出すときに参照する。
**「通常業務では採らない手法」** は ⚠ を付けた。ISUCON の採点ルール（ベンチマーカーが検査する整合性・再起動後のデータ保持）の範囲では正当だが、ルールの読み違いで fail になりやすいので、必ず当日マニュアルの該当箇所を根拠にする。
（実績）は過去の実測で効果を確認したもの。

## 進め方の原則
- 計測してから直す。`summary.md` の占有率が大きいものから。合計時間が大きくても採点に効かないエンドポイントは後回し
- 採点ルールを先に読む：どのリクエストが加点か、エラー・タイムアウトの減点、**データの反映をどこまで遅らせてよいか**（キャッシュの許容範囲を決める）、再起動試験の有無
- 1つずつ入れて測る。複数を同時に入れると、どれが効いたか分からなくなる

## キャッシュ

### ⚠ ZTC（Zero Time Cache）
同じ重い計算への同時リクエストを、**整合性を壊さずに**1回の計算にまとめる手法。有効期限が 0 秒のキャッシュ、という意味で呼ばれる。考え方の出典は methane の zerotimecache（https://qiita.com/methane/items/27ccaee5b989fb5fca72）。
- 前提：多くの問題の整合性は「リクエストが届く前に完了した書き込みは、レスポンスに反映されていること」。逆に言えば、**リクエストが届いた後に始まった計算の結果なら、使い回しても古くない**
- 仕組み：キーごとに「実行中の計算」と「次の計算」を持つ
  1. 計算が実行中でなければ、自分で計算を始める
  2. 実行中なら、それには相乗りしない（自分が届く前に始まっていて、古い可能性がある）。**次の計算**に相乗りして待つ
  3. 実行中の計算が終わったら、待っていた全員分の「次の計算」を1回だけ走らせ、全員に同じ結果を返す
- 効果：同時に N 件来ても、計算は高々2回分の時間で済む。キャッシュの破棄（invalidation）を考えなくてよい
- 素の singleflight（実行中の計算に相乗りする）との違い：singleflight は、自分が届く前に始まった計算の結果を受け取ることがあるので、計算時間分だけ古くなりうる。反映の遅延が許されている問題なら singleflight で足りる（その方が速い）
- 向くもの：ランキング・集計・タイムラインなど、読み込みが集中し計算が重いもの。向かないもの：ユーザーごとに結果が違うもの（キーが分散して相乗りが起きない）
- 実装：**手書きしない**（並行制御の誤りで fail しやすい）。Go なら [motoki317/sc](https://github.com/motoki317/sc) を使う
  - ZTC：`sc.New(fetch, 0, 0, sc.EnableStrictCoalescing())`（freshFor・ttl を 0 にし、strict coalescing で「先に始まった計算の結果」を後から来た呼び出しに渡さない）
  - 反映の遅延が許される場合：`sc.New(fetch, freshFor, ttl)`。freshFor 内はキャッシュ、ttl 内は古い値を返しつつ裏で1本だけ再取得（stale-while-revalidate）
  - 書き込み時に `cache.Forget(key)` で破棄できる。容量制限は `sc.WithLRUBackend(n)`
  - Go 以外は、キーごとの mutex と世代番号で同じ動作を書く

### ⚠ 反映の遅延の許容を使い切る
マニュアルに「N 秒以内に反映されればよい」とあれば、その範囲で TTL キャッシュにする（Go なら sc の freshFor/ttl）。許容が書かれていなければ使わない（整合性チェックで fail になる）。

### オンメモリキャッシュ
- 変更がほぼ無いマスタ（ユーザー情報、設定値など）はプロセス内に持つ。（実績）
- 再起動試験があるなら、**起動時に DB から読み直す**こと。書き込みをメモリだけに持つのは不可
- アプリが複数台なら、台ごとにキャッシュがずれる。書き込みが絡むキャッシュは、nginx の `hash $cookie_xxx consistent;` で同じユーザーを同じ台に寄せるか、共有先（DB・Redis など）に置く

### HTTP キャッシュ
- 静的ファイルの `Cache-Control`・`ETag`・`304` は、ベンチマーカーが尊重するかを当日マニュアルで確認してから
- 画像などを DB に入れている問題は、**ファイルに書き出して nginx から直接返す**（実績：private-isu の画像で大幅改善）。認可が要るものはアプリが判定して `X-Accel-Redirect` で nginx に返させる

## DB
- インデックス：`summary.md` の「走査行/回」が「返却行/回」より桁違いに大きいクエリ、`noindex`（インデックス未使用）が多いクエリから。複合インデックスは WHERE の等値 → 範囲 → ORDER BY の順。（実績）
- ⚠ オプティマイザの選択を固定する：`STRAIGHT_JOIN`・`FORCE INDEX`。データ分布を知っている前提で決め打ちする。（実績：private-isu の getIndex で users を全件スキャンして駆動表にしていたのを、posts の `created_at` インデックスから引く形に固定し、スコア約1.5倍）
- N+1 をやめる：ループ内のクエリを `IN (...)` か JOIN にまとめる。（実績）
- ⚠ 非正規化：件数・最新値などを別カラムや別テーブルに持ち、書き込み時に更新する。COUNT(*) の集計クエリを消す
- バルク INSERT、不要な `SELECT *` をやめる（大きい BLOB 列を読まない）。（実績）
- ⚠ 耐久性を下げる設定（`innodb_flush_log_at_trx_commit=2`、doublewrite・binlog を切る）。要件は「再起動後にデータが残る」ことだけなので許される（`knowledge/middleware.md`）
- 構成：DB を別ホストに分けると、アプリと CPU を取り合わなくなる。分けたら接続数と RTT が増えるので、接続プールと N+1 の解消を先に

## アプリ
- 接続プール：Go なら `SetMaxOpenConns`・`SetMaxIdleConns` を十分に、DSN に `interpolateParams=true`（prepare の往復を消す）。（実績）
- 外部コマンドの実行（`exec` で openssl などを呼ぶ）をライブラリ関数に置き換える。（実績：private-isu のパスワードのハッシュ）
- テンプレートの描画・JSON のエンコードが CPU の上位なら、事前に組み立てる・軽いライブラリに替える。（実績：private-isu ではテンプレートが CPU の約半分）
- ⚠ 書き込みの非同期化・まとめ書き：再起動でデータが消えない設計にすること。再起動試験のリスクが高い（`[restart]` 扱い）
- クライアントへの待ち時間の指示（`retry_after` のような値、ポーリング間隔）を伸ばし、通知などをまとめて返して、リクエスト数そのものを減らす。ベンチマーカーがその値に従うことをマニュアルかアクセスログの間隔で確かめる。（待ち時間を数十倍に伸ばして大きく伸びた過去の例がある。ローカルの予測は負に出やすいので、それだけで見送らない）
- ⚠ `/initialize` で重い前処理をする：ベンチ開始時に呼ばれ、時間制限内なら何をしてもよい。非正規化テーブルの作成、キャッシュの温め、インデックスの追加など

## Web サーバ・ネットワーク
- nginx → アプリの keepalive（`keepalive` + `proxy_http_version 1.1` + `Connection ""`）。（実績：+10%）
- 同じホストなら Unix ドメインソケット（`templates/snippets/unix-domain-socket.md`）
- 静的ファイルは nginx から、`gzip_static` で事前圧縮したものを返す。動的 gzip は CPU を食う
- ファイルディスクリプタ・接続数の上限（nginx `worker_rlimit_nofile`、systemd `LimitNOFILE`、`net.core.somaxconn`）。エラーログに `Too many open files` や接続拒否が出たら

## 複数台構成
- まず1台で詰めて、CPU が飽和している役割から別ホストへ分ける（`resources.json` でどのプロセスが飽和しているかを見る）。DB が CPU を占めているなら、DB の別ホスト化は最も効く打ち手の1つ（これだけでスコアが約2倍になった過去の例がある）。台数があるのに1台に集まったままにしない
- よくある形：nginx + アプリ ×2〜3、DB 専用1台。nginx の upstream で weight を付けて振り分ける
- 画像などのファイルを書き込む処理は、1台に寄せるか共有する（台ごとに書くと他の台から読めない）

## ⚠ ベンチマーカーの挙動を観測から読む
ベンチマーカーの実装は見られない。代わりにアクセスログから、どのユーザーがどの順にリクエストしているかを再構成すると、シナリオと並列度が分かる。
- アクセスログに cookie やユーザー識別子を出し、ユーザーごとにリクエストの開始〜終了を時系列に並べて可視化する（以前 `archive/script/accesslog-parser` で作った。LTSV 前提）
- タイムアウトやエラーで減点が大きいなら、処理しきれないリクエストを早く失敗させる方が得なこともある（採点ルールで確認してから）
