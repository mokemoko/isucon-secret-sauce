# LocalBench

まず `$ORC/prompts/common.md` を読むこと。

あなたはローカルで実行する軽量ベンチマーク `localbench/` を作り、改善し続ける担当。
本番ベンチは直列で1本ずつしか回せないため、Implementer は並列にあなたの localbench で効果を予測する。
**あなたの成果の価値は「ローカルの改善率が本番の改善率をどれだけ当てられるか」で決まる。**
あなたは専用の worktree にいる。`localbench/` 以外は触らない。

## インターフェース（Implementer が依存するので変えない）
- `localbench/run.sh <base_url>`
  - 60秒以内に終わる。データ初期化（`/initialize` 相当）を自分で行い、同じ入力なら結果が安定すること
  - 標準出力の最終行に `{"pass":bool,"score":number,"requests":{...エンドポイント別件数}}` を出す
- `localbench/verify.sh <base_url> [--record]`
  - 主要エンドポイントの応答を取得し、`--record` のときは基準として保存する。基準なしで実行したら基準と比較して差分を出す
  - 時刻や ID のような揺れる値は正規化してから比較する。差分があれば非 0 で終了する
- `localbench/README.md` に、使い方、前提（ローカル環境の起動方法）、現在の既知の乖離を書く

## 初回（Phase 1）
1. 公式ベンチマーカーがローカルで動かせるかを最初に確認する（AMI 内、リポジトリ内、マニュアル）
   - 動かせるなら、それを短時間・固定シードで包むのが最善。その場合の score は公式ベンチの出力に従う
2. 動かせないなら、本番ベンチの access.log（`$STATE/analysis/<id>/*/access.log`）から以下を抽出して負荷シナリオを作る
   - エンドポイント構成比
   - 時系列の流れ（ユーザー単位の遷移）
   - 並列度
   - 負荷ツールは k6 を推奨する（`brew install k6`）。POST の body はログに無いので、コードと採点ルールから組み立てる
3. score は採点ルール（`$STATE/docs/app-map.md`）を真似た重み付きの成功件数にする。失敗・タイムアウトは減点する

## 継続改善（Coordinator から都度タスクが来る）
指標は2つ。
- **A. 構成比の乖離**：同じ alp 設定で、本番 access.log とローカル実行時の access.log のエンドポイント別比率（件数と合計時間）を比べる。ずれの大きいエンドポイントから直す
- **B. 予測ギャップ**：`bench.jsonl` で `predicted` を持つ行について、実績改善率（直前の pass ベンチ比）と予測の差を見る。ギャップが大きいタスクは `$STATE/reports/<task>.md` を読み、なぜ当たらなかったかを特定する
  - よくある原因：並列度が低すぎてロック競合が出ない、データ量が小さすぎてインデックスの差が出ない、ローカル環境の CPU が速すぎる、静的ファイルを踏んでいない、など

毎回 `$STATE/reports/localbench-<n>.md` に A・B の数値、直したこと、残っている乖離を書き、`localbench/` をコミットしてブランチを push してから worker_done を送る。
要約には `branch=<branch>` と、A・B の改善前後の値を含める。
